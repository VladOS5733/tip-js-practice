3. Реализация
3.1. HTTP-клиент
Клиент (src/api-client.js) реализует базовый метод requestJson, поддерживающий методы GET, POST, PATCH и DELETE. При передаче тела запроса автоматически устанавливается заголовок Content-Type: application/json и выполняется сериализация объекта через JSON.stringify. Ответ с кодом 204 No Content корректно обрабатывается и возвращает null. Предусмотрена настройка тайм-аута с помощью setTimeout и AbortController, а также поддержка внешней отмены через передачу пользовательского signal.

3.2. Доменный API
Доменный модуль (src/task-api.js) инкапсулирует эндпоинты задач и категорий. Реализованы операции: getTasks (с валидацией и нормализацией фильтров), getTaskById, getCategories, loadInitialData (параллельная загрузка задач и категорий через Promise.all), createTask, updateTask, setTaskCompleted, deleteTask и resetDemoData. Схема ответа проверяется в самом task-api.js (функции isTask и isCategory): проверяется тип данных, корректность id, отсутствие дубликатов и соответствие meta.total реальному количеству элементов.

3.3. Состояния интерфейса
Интерфейс управляется через адаптер dom-app.js и контроллер app-controller.js:

loading: панель списка задач получает атрибут aria-busy="true", отображается сообщение о загрузке.

ready: данные успешно получены, список задач отрисовывается на странице.

empty: запрос выполнен успешно, но массив данных пуст (например, при поиске не найдено совпадений). Отображается соответствующее сообщение.

error: возникла сетевая ошибка или ошибка сервера. Отображается текст ошибки и кнопка «Повторить загрузку», которая вызывает метод refresh() контроллера.

3.4. Изменение данных
При создании (POST), редактировании (PATCH), смене статуса и удалении (DELETE) задача отправляется соответствующий HTTP-запрос. Во время выполнения мутации интерфейс блокируется (кнопки становятся неактивными с помощью setMutationPending). После успешного ответа сервера контроллер не изменяет список вручную, а заново запрашивает данные через fetchList(). Это гарантирует, что интерфейс отображает только актуальное состояние сервера.

3.5. Защита от устаревшего ответа
При каждом новом запросе данных (например, при быстром переключении фильтров) в app-controller.js создается новый экземпляр AbortController. Предыдущий контроллер вызывает метод abort(), отменяя старый сетевой запрос. Кроме того, после получения ответа выполняется проверка if (currentRequest.signal.aborted) return;. Это предотвращает ситуацию, когда медленный старый ответ приходит позже быстрого нового и перезаписывает актуальные данные в интерфейсе (Race Condition).

6. Ответы на контрольные вопросы
Почему fetch не отклоняет Promise при ответе 404?
fetch отклоняет Promise (переводит его в состояние rejected) только при сетевых ошибках (например, нет соединения с сервером или запрос заблокирован CORS). Если сервер ответил, но с HTTP-статусом 404 (Not Found), 500 (Internal Server Error) и т.д., fetch считает, что запрос прошел успешно, и возвращает объект Response с response.ok === false. Поэтому программист должен сам проверять response.ok и генерировать ошибку вручную.

Почему ответ 204 нельзя разбирать вызовом response.json()?
Статус 204 означает «No Content» (Нет содержимого). Тело ответа абсолютно пустое. Если вызвать response.json(), метод попытается распарсить пустую строку как JSON и выбросит исключение SyntaxError. Для ответов 204 нужно просто возвращать null.

Чем состояние empty отличается от error?
Состояние empty означает, что запрос прошел успешно (HTTP 200), но сервер вернул пустой массив данных (например, фильтр отсеял все задачи). Состояние error означает, что запрос не удался из-за технической проблемы (нет сети, тайм-аут, сервер вернул 500).

Зачем отменять предыдущий запрос при смене фильтров?
Чтобы избежать состояния гонки (Race Condition). Если пользователь быстро меняет фильтры, запросы уходят один за другим. Ответ на первый (медленный) запрос может прийти позже, чем на второй. Без отмены старый ответ перезапишет новые данные в интерфейсе, и пользователь увидит неверный результат.

Почему после мутации список повторно запрашивается у API?
Сервер является единственным источником истины (Single Source of Truth). При создании задачи сервер сам присваивает ей id, а при изменении может применять дополнительную логику. Повторный запрос списка гарантирует, что интерфейс отобразит ровно то состояние, которое сейчас хранится в базе данных, исключая рассинхронизацию.
